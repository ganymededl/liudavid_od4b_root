01 · Plan and configure agent solutions · 30–35%

Design a safe, useful agent

Start with a bounded business outcome. Define internal or external audience, supported tasks, escalation, channels, and deployment needs. List enterprise systems and reusable components before choosing tools. Separate maker permissions, the signed-in user's access, and the connection identity used by each action.

Identity, governance, and responsible AI

Authentication establishes who is acting; authorization decides what that identity may access. A signed-in user is not automatically allowed to read every source or execute every action. Preserve source permissions and test access with different roles.

Use least privilege and approved environments and connectors. Data policies (often called DLP) govern connector use and data movement; they do not replace authorization checks. Define sensitive-data handling, retention, transparent limitations, and human escalation. Treat retrieved text as untrusted data—not instructions to override policy.

Agent flows, topics, and response design

A topic manages a conversation path with variables, conditions, tools, knowledge, and responses. An agent flow performs work through mapped inputs, actions, and outputs. A topic can call a flow; avoid confusing the conversational path with the transaction.

For a flow, define inputs and outputs, connect actions, validate data, handle failures, and use human review for consequential work. Test approval, rejection, timeout, and connector-error paths. Inspect run history rather than assuming a friendly response means the action succeeded.

Use generative answers for grounded synthesis, custom prompts for a focused transformation, HTTP/API requests for endpoint calls, and adaptive cards for structured display or input. Validate card outputs and missing values before using them in actions.

Try it · Design an employee request assistant

In an approved nonproduction environment with synthetic data, sketch an internal assistant that explains a policy and creates a mock request. Define allowed roles, the knowledge source, the action identity, one approval step, and a fallback. Build a simple topic and a flow that accepts a request type and returns a mock reference.

Evidence to keep: an architecture sketch, input/output mapping, and test results for an allowed request, missing input, denied access, and rejection. Explain why a public anonymous design would need different access boundaries.

02 · Integrate and extend agents in Copilot Studio · 40–45%

Choose the right integration—not just an available one

Knowledge versus actions

Knowledge grounding retrieves evidence to answer a question. A tool or action performs work or retrieves structured data through a defined operation. “Explain our return policy” and “submit a return” require different capabilities and safeguards.

  • Copilot connectors: make enterprise content available through supported Microsoft 365/Copilot knowledge integrations. Check source indexing, identity, and permission behavior.
  • Power Platform connectors: expose service capabilities, including supported data and action operations. Review the connector's supported knowledge or tool use and connection identity.
  • Azure AI Search: retrieval over an indexed corpus. Check index quality, connection authorization, relevance, and citations; do not assume an index automatically preserves every source permission.
Connectors, REST APIs, MCP, and computer use

Reuse a governed custom connector when it already fits. Use a supported REST API integration for an endpoint with a clear schema and authentication model. MCP (Model Context Protocol) exposes tools through a standard interface; still inspect permissions, descriptions, inputs, outputs, and failure behavior.

Computer use interacts with an application UI. Consider it when appropriate interfaces are unavailable; UI changes, credentials, and unexpected screens create extra risks. Bound actions to approved applications, use nonproduction identities, monitor execution, and stop or escalate on uncertainty. Never treat computer use as a shortcut around authorization.

Multi-agent collaboration and Azure

Give each specialist a distinct responsibility and define routing, handoff inputs/outputs, timeout, and fallback. Reuse existing Copilot Studio agents where appropriate. Foundry agents support specialist agent capabilities; Fabric data agents support governed analytical questions. A2A (agent-to-agent) supports agent interoperability; MCP is primarily a tool interface, not the same collaboration contract.

Azure AI Search provides retrieval; the Foundry model catalog supports model selection for supported custom prompt scenarios; Application Insights provides runtime telemetry. Choosing a model does not grant data access or ensure grounding. Check region, licensing, availability, and identity requirements in current documentation.

Try it · Compare two integration designs

Using synthetic policy documents and a mock order service, draw one path to answer a policy question and another to retrieve an order status. Choose a knowledge source and a tool separately; document schemas, identity, permission checks, and failure responses. Then sketch a handoff to an analytical specialist.

Evidence to keep: a decision table explaining why you selected a connector, API, or MCP interface; a denied-access test; and a failed-handoff response. If resources are available, test a small approved sample index and inspect retrieval and telemetry. A paper walkthrough is fine when you lack access.

03 · Test and manage agents · 20–25%

Prove quality, then move changes safely

Evaluation and operational evidence

Create representative test sets covering normal questions, ambiguity, missing knowledge, denied access, unsafe requests, tool failure, and handoff failure. Choose evaluation methods and success criteria before running tests. Inspect failed results, categorize causes, make a targeted change, then rerun the same tests to compare outcomes.

Evaluation checks response and task quality against test cases. Monitoring observes runtime health, latency, and failures. Use flow run history for a failed action, Application Insights for telemetry, and evaluation results for quality regressions. Collect only appropriate data and avoid unnecessary sensitive content in logs.

Application lifecycle management (ALM)

Package agents and dependencies in solutions. Use environment variables for environment-specific settings and connection references to bind connector connections. Neither mechanism is a blanket secret store: use approved credential handling. Validate dependencies and target settings when moving changes through Power Platform Pipelines.

Separate development, test, and production. Test permissions, connections, and user journeys after deployment and before activation. Keep a versioned baseline and a recovery plan; successful import alone is not proof of runtime correctness.

Try it · Run a controlled improvement cycle

Write six synthetic test cases: two normal, one ambiguous, one denied-access, one missing-knowledge, and one failed-tool case. Define the expected behavior for each. Run a baseline, change one instruction or tool mapping, and rerun. Walk through packaging the agent and dependencies in a solution with target environment values.

Evidence to keep: a before/after results table, one categorized failure, and a deployment checklist with connection validation and a recovery step.

Quick glossary

Grounding
Using retrieved evidence to inform an answer; still verify relevance and access.
Orchestration
Selecting and coordinating conversation paths, tools, and specialist agents.
Connection reference
A solution component referring to a connector connection for environment-aware use.
Environment variable
A configurable value that can differ between environments.
MCP / A2A
Tool interoperability / agent-to-agent interoperability; choose by what must communicate.
Test set
A repeatable collection of cases used to assess behavior and compare changes.
Telemetry
Operational signals such as failures, latency, and execution events.
Least privilege
Granting only the access necessary for a defined task.
